# RunbookLatch

[Canonical contract](https://explorer-studio.genlayer.com/address/0xFd69830d264aA81B108FAF5631347a104E53dDC9) · [Network evidence](evidence/studionet.json) · [Validation](VALIDATION.md)

A standalone GenLayer Intelligent Contract that compiles natural-language runbook prerequisites into a shared dependency graph, rejects cycles and ambiguous rules, and enforces who may acknowledge each step and when.

A release instruction such as “do not distribute until the bundle is assembled and the release notes are checked” creates two mandatory predecessors. Completing only one cannot unlock distribution. Either preparation may finish first.

## Why consensus matters

Action names in a procedure do not always match an integration's step names. “Distribution” may refer to a “publish” step; “release-note verification” may refer to “review.” Validators independently interpret the procedure against the immutable action catalog, rather than accepting an owner's graph or a leader's formatting.

Every ordered pair of distinct steps is classified REQUIRED, NO_DIRECT or UNCLEAR. Models select rule-line indices; contract code extracts the exact source quotations, preventing paraphrased text from becoming evidence. Validators re-run the complete interpretation, require exact agreement on every category, and separately check proposed quotations against the original procedure and action pair. Deterministic code then computes graph edges, detects cycles, calculates parallel layers and enforces all predecessor acknowledgements.

The owner has no override. A cycle or any unclear relation prevents all acknowledgements. A compiled graph cannot be edited. Stored explanations may vary between nodes; the complete ordered category vector must agree.

## Use

Deploy `contracts/runbook_latch.py` with no constructor arguments on **Stable Studionet, chain 61999**.

1. Call `open_run(run_id, plan_json)` from the owner wallet. Start from `examples/release.json`, replacing executor addresses with the intended wallets. It is an illustrative input, not an already-signed run.
2. The owner or a named executor calls `compile_run(owner, run_id)`. Wait for a successful finalized majority-agree result.
3. Read `get_run(owner, run_id)`. Inspect findings, graph, graph digest and `available`. ACTIVE permits acknowledgements; REVIEW and CYCLE do not.
4. Each step's named executor calls `acknowledge(owner, run_id, step_id, graph_digest, note)` only after its work is complete. All predecessors must already be acknowledged. Copy the exact graph digest from the record.
5. The final acknowledgement changes status to COMPLETE. Read the append-only journal, which preserves actor, note and ordinal for every step.

This records signed assertions of completion. It does not execute a shell command, publish an archive, verify a checksum or independently prove that work occurred.

## Methods

| Method | Kind | Arguments |
|---|---|---|
| open_run | write | run_id, plan_json |
| compile_run | write | owner, run_id |
| acknowledge | write | owner, run_id, step_id, graph_digest, note |
| get_run | view | owner, run_id |
| get_protocol | view | none; returns `runbooklatch-1` |

All arguments are strings. `get_run` returns a JSON string with a derived `available` list. Owner/ID namespaces isolate records. Compile is allowed once, by an owner or executor. Acknowledgements are one-shot and cannot be revoked. New or corrected procedures require a fresh run ID. See [PROTOCOL.md](PROTOCOL.md) for definitions and exact bounds.

## Validation

```sh
python -m unittest discover -s tests -v
pip install -r requirements-dev.txt
genvm-lint check contracts/runbook_latch.py
python scripts/prepare-sdk.py
python sdk-tests/check_sdk.py
npm ci
node scripts/read-live.mjs
```

The 21 mocked-host tests execute the actual contract and include all 64 directed binary graphs on three nodes, checked against an independent permutation oracle. Available-step calculation is checked for every completion subset. Additional checks cover conjunction, parallel order, transitive gating, permissions, replay, immutable inputs, digests, malformed findings, unsupported quotes and independent validator disagreement.

The SDK check uses pinned real storage and calldata with mocked model responses. These local checks do not establish live consensus. `schema.json` is generated by the official linter. Actual network evidence is in [evidence/studionet.json](evidence/studionet.json); [VALIDATION.md](VALIDATION.md) distinguishes observed network results from local coverage.

`read-live.mjs` is read-only. `verify-live.mjs` is a development write harness: it requires `RUNBOOKLATCH_NEW=1` once to start a dedicated zero-value run, keeps test signing keys in a private local state file outside the repository, persists each intent and hash before polling, and resumes existing hashes. An unknown send outcome remains blocked. Inspect failures before making a new explicit attempt. Do not use the write harness merely to inspect the published example. No automatic resend or Appeal exists.

## Boundaries

- The graph formalizes **stated direct prerequisites** only. NO_DIRECT means no direct constraint was found, not permission, operational safety or real-world independence. Paths enforce transitive ordering without adding redundant semantic edges.
- Only unconditional, conjunctive prerequisites between distinct declared steps are supported. Self-dependencies are outside the pair matrix and must not be submitted; they are not covered by the graph cycle check. Conditional, OR, unrepresented external or ambiguous prerequisites require REVIEW. Detection of such wording relies on semantic consensus and can fail.
- Owner-selected procedures, action descriptions and executor addresses are unverified assertions. A wallet is not a verified identity or independent organization. The owner can choose itself as executor for all steps; this does not remove dependency gates.
- Completion is an executor's public acknowledgement, not proof of physical or digital work. False acknowledgements and colluding executors remain possible. Off-chain systems must enforce their own access controls and verify authenticated finalized state before relying on a record.
- No actual operations, token transfers, escrow, secrets or private data are handled. Do not use this bounded prototype for safety-critical operations. All procedure text and notes are public and immutable.
- No cancellation, expiry, reassignment, retries, conditional branches or graph revisions. An unavailable executor can stall a run. Each run is bounded to six steps and 30 ordered relations; total runs per deployment are unbounded.
- Inputs are untrusted prompt data. Model mistakes, prompt injection and correlated validator errors remain possible. Failed consensus writes no compiled graph. Majority agreement does not certify procedure correctness or completeness.
